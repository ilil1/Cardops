# BankChurners 기반 구현의 한계와 데이터 전환 배경

이 문서는 기존 BankChurners 데이터로 CardOps를 구성했을 때의 문제점과, 이를 개선하기 위해 새로운 데이터로 예측·검증 구조를 다시 만드는 이유를 정리합니다.

진단 대상은 **BankChurners 기반 분석·캠페인 운영 프로토타입**입니다. 새로운 Synchrony 실험에서 구현한 부분과 앞으로 반영할 부분은 마지막 절에 구분해 두었습니다.

## 1. 시뮬레이션을 오해하게 만들 수 있는 부분

### 1.1 분류 모델은 이미 기록된 이탈 고객의 특성을 구분한다

`BankChurners.csv`는 고객별 한 행으로 된 정적 데이터입니다. 고객 특성이 **언제 관측됐는지**, 그 뒤 **언제 이탈했는지**를 연결할 월별 기록이 없습니다. 분류 모델도 고객 행을 무작위로 나눠 평가하므로, 높은 점수는 이 데이터에서 기록된 이탈·비이탈 고객을 잘 구분했다는 의미입니다.

따라서 이 모델을 월별 데이터를 받아 “다음 달이나 3개월 안에 이탈할 고객”을 미리 찾는 시뮬레이션으로 해석할 근거는 부족합니다. 모델이 높은 위험 점수를 부여한 고객은 데이터에 기록된 이탈 고객과 비슷한 특성을 가진 고객으로 해석하는 것이 적절합니다.

현재 모델은 프로토타입에서 “**고객 프로필을 바탕으로 위험 점수를 계산하는 흐름**”을 보여줄 수 있습니다. 그러나 “**월별 변화로 미래 이탈을 조기 경보한다**”고 표현하면 실제 구현과 검증 범위를 넘어섭니다.

근거: [분류 모델의 데이터 분할](../../src/final/classification_final.py) · [BankChurners 원본](../../data/raw/BankChurners.csv)

### 1.2 이미 이탈한 고객이 유지 캠페인 후보처럼 보일 수 있다

원본에는 `Attrition_Flag`로 이탈 여부가 기록되어 있지만, 기존 고객 DB 적재 필드에는 이 정보가 포함되지 않습니다. 이후 분석 배치는 적재된 고객을 대상으로 점수를 계산합니다. 이 과정에서 이미 이탈한 고객과 아직 거래 중인 고객을 캠페인 자격 기준으로 구별하지 못할 수 있습니다.

기존 분석 기록에서는 원본과 모델 산출물을 대조했을 때 **고위험 점수를 받은 1,579명 중 1,549명이 원본에서 이미 이탈 고객**이었습니다.

> 이 수치는 당시 원본 데이터에 모델을 적용한 분석 기록입니다. 현재 DB 인원수나 새 Synchrony 모델의 평가 결과가 아니며, 이번 문서 정리에서 다시 집계한 값도 아닙니다.

가상 회사의 캠페인 시나리오에서도 이탈 고객과 아직 거래 중인 고객을 구별하지 않으면 이탈 방지 캠페인의 대상이 부정확해집니다. 원본의 이탈 여부는 모델 입력값으로 쓰지 않더라도, **시연 대상이 아직 거래 중인 고객인지 구분하는 데** 활용할 필요가 있습니다.

새 데이터로 전환할 때에도 예측 기준일에 이미 해지한 고객을 제외하는 규칙을 모델 실험과 실제 캠페인 대상 선정에 모두 반영해야 합니다.

근거: [고객 데이터 적재 필드](../../backend/ai-service/cardops_ai/app/customer_import.py) · [분석 대상 점수화](../../backend/ai-service/cardops_ai/app/analysis_batch.py)

### 1.3 회귀 모델의 활동성 갭은 월별 하락이 아니다

기존 회귀 모델은 데이터에 담긴 **최근 12개월 거래건수**를 추정하고, 같은 구간의 실제 거래건수와 비교해 활동성 갭을 계산합니다.

```text
활동성 갭 = 실제 거래건수 − 모델이 예상한 거래건수
```

갭이 낮다는 것은 **같은 12개월 구간에서 모델 예상보다 거래가 적었다**는 뜻입니다. 지난달보다 거래가 줄었다거나 곧 이탈한다는 의미를 직접 제공하지는 않습니다.

하위 20% 기준도 모델이 찾아낸 이탈 경계가 아니라 업무 규칙으로 정한 상대 기준입니다. 화면에서 이를 ‘활동성 하락’이나 ‘이탈 징후’처럼 읽히게 하면 실제 계산보다 강한 의미를 전달할 수 있습니다.

현재 지표의 설명은 “**모델 예상 대비 거래량 차이**”가 적절합니다. 월별 하락이나 다음 달 거래량을 다루려면 서로 다른 관측 기간을 구분할 수 있는 기록과 그에 맞는 정답을 구성해야 합니다.

근거: [회귀 목표값 정의](../../src/feature_engine/regression_features.py) · [활동성 갭 계산](../../backend/ai-service/cardops_ai/app/analysis_batch.py)

### 1.4 군집 이름과 추천 행동은 모델이 효과를 확인해 준 것이 아니다

군집 모델은 비슷한 고객을 묶을 수 있습니다. 그러나 군집에 ‘우량’, ‘우선 관리’ 같은 이름을 붙이거나 업셀링·재활성화 행동을 연결하는 것은 별도의 업무 규칙입니다.

기존 활동성 갭 군집은 거래량과 예상 대비 거래 차이 등을 사용합니다. 따라서 군집 이름이 실제 사업 가치나 캠페인 반응을 검증한 결과는 아닙니다. 특히 ‘거래 감소’라는 이름만으로 실제 월별 거래 감소가 관측되었다고 해석해서는 안 됩니다.

프로토타입에서 추천 행동은 “**이 군집에 적용해 볼 업무 시나리오**”로 설명하는 것이 적절합니다. 모델이 효과적인 행동을 학습했다고 설명하려면 고객에게 어떤 행동을 적용했고 그 결과가 어땠는지 별도 관측과 검증이 필요합니다.

근거: [군집 라벨과 권장 행동 부여](../../backend/ai-service/cardops_ai/app/analysis_batch.py)

### 1.5 합성 데이터의 결과는 시연용 가정이다

합성 고객 생성은 기존 모델의 위험 점수 분포를 고려하고, 데모 캠페인은 설정한 규칙에 따라 전환·유지 결과를 만듭니다. 이 방식은 화면과 업무 흐름을 시연하는 데 사용할 수 있습니다.

다만 합성 고객을 모델 예측에 맞춰 생성하고 캠페인 결과도 미리 둔 가정에 따라 정하면, **그 데이터로 다시 모델의 성능이나 캠페인 효과를 입증할 수는 없습니다.** 평가할 모델이나 효과에 관한 가정이 데이터 생성에 이미 들어가 있기 때문입니다.

시연 자체는 가능하지만, 대시보드의 수치가 **합성 시나리오의 결과**라는 점을 사용자가 분명하게 알 수 있어야 합니다. 실제로 관측한 거래·해지 결과와 가정으로 생성한 캠페인 결과는 출처와 해석 범위를 표시해야 합니다.

근거: [합성 고객 생성](../../backend/ai-service/cardops_ai/scripts/generate_synthetic_customers.py) · [데모 캠페인 결과 생성](../../backend/ai-service/cardops_ai/scripts/seed_demo_campaign.py)

## 2. 월별 MLOps 시뮬레이션에서 부족했던 점

기존 `as_of_date`는 분석 기준일을 기록하고 해당 날짜의 저장된 스냅샷을 조회하는 데 사용할 수 있습니다. 그러나 BankChurners의 원본 고객 특성이 실제로 어느 월의 상태였는지를 알려주지는 않습니다.

따라서 날짜가 저장된다는 이유만으로 **“1월 데이터를 학습해 2월을 예측했다”는 시계열 검증**이 성립하지 않습니다. 동일한 정적 고객 정보를 여러 날짜에 저장해도 실제 고객의 월별 이용 이력이 생기는 것은 아닙니다.

월별 데이터가 들어오는 모습을 합성해 보여줄 수는 있습니다. 이때는 월별 기록과 미래 결과를 만드는 규칙 자체가 시뮬레이션의 가정입니다. 이 가정으로 데이터 파이프라인·재학습·배포·모니터링 흐름을 시연할 수 있지만, 미래 이탈을 실제로 잘 예측한다는 증거로 사용하려면 별도 데이터와 검증이 필요합니다.

근거: [분석 배치 날짜와 스냅샷 처리](../../backend/ai-service/cardops_ai/app/analysis_batch.py)

## 3. 기존 구현을 설명할 때의 기준

BankChurners 기반 모델로 보여줄 수 있는 범위는 다음과 같습니다.

- 고객 프로필에 따른 위험 점수 산출
- 모델 예상 대비 거래량 차이 계산
- 특성이 비슷한 고객의 군집 분류
- 캠페인 대상 선정·배정·처리·이력 관리
- 가정을 명시한 캠페인 성과 지표 시뮬레이션

이 결과를 “월별 활동 하락에 따른 미래 이탈 예측”이나 “캠페인으로 이탈을 방지한 실증 성과”로 설명하면 근거를 넘어섭니다.

따라서 기존 구현은 “**정적 고객 데이터로 만든 분석·캠페인 운영 프로토타입**”으로 설명하는 것이 정확합니다. 월별 합성 데이터를 사용하는 시연에서는 데이터 생성 가정과 시뮬레이션 결과를 명시하고, BankChurners 분류 성능과 별도로 해석해야 합니다.

## 4. 이 한계를 개선하기 위한 새로운 작업

CardOps의 목표는 **카드를 아직 해지하지 않은 고객의 과거 이용 기록으로 향후 해지 위험을 예측하고, 이후 관측된 결과로 모델을 평가하는 것**입니다. 이를 위해 고객 특성의 관측 시점, 예측 기준일, 실제 해지일을 연결할 수 있는 데이터 구조가 필요합니다.

현재는 날짜별 거래와 카드 발급·해지일이 있는 Synchrony 데이터로 이 구조를 구현하고 있습니다. 기존 로그인·권한·고객 조회·캠페인 이력 등의 서비스 기반은 재사용하고, 데이터 적재와 모델 입력·정답·평가 방식은 새 데이터에 맞춰 구성하는 방향입니다.

### 4.1 기존 문제와 현재 대응

| 기존 문제 | 개선 방향 | 현재 진행 상태 |
| --- | --- | --- |
| 정적 이탈 상태 분류를 미래 예측으로 해석 | 기준일까지의 거래로 이후 30일·60일 해지를 예측 | 입력·정답 생성과 분류 모델 비교 구현 |
| 이미 이탈한 고객이 유지 대상에 섞임 | 기준일에 발급되어 있고 아직 해지하지 않은 고객만 선정 | 실험의 대상 필터에 적용. 서비스 DB·타기팅 연결은 남아 있음 |
| 같은 기간의 활동성 갭을 월별 하락으로 해석 | 기간별 이용 변화를 계산하고 다음 달 거래량을 별도 정답으로 구성 | 변화 특징과 다음 달 거래건수·금액 정답 생성 구현. 새로운 회귀 모델 학습·평가는 후속 범위 |
| 군집 이름을 고객 가치·행동 효과로 해석 | 행동 유형 설명과 캠페인 효과 검증을 구분 | 새 군집 모델 검증과 화면 반영은 후속 범위 |
| 합성 결과를 성능·효과의 증거로 사용 | 원본 파일의 거래·해지 기록으로 평가하고 합성 시연의 가정을 표시 | 새 분류 실험은 기록된 해지일로 평가. 캠페인 효과 검증은 별도 과제 |
| 분석 날짜만으로 월별 검증을 주장 | 거래 발생일로 상태를 구성하고 결과 관측 이후 학습·평가 | 월별 스냅샷·시간순 재학습 비교·동결 모델 평가 구현. 자동 운영 파이프라인은 후속 범위 |

### 4.2 예측 기준일과 미래 정답의 예시

**2026-03-31이 끝난 시점에 향후 30일 내 해지를 예측**한다면 다음과 같이 구성합니다.

1. **대상 고객**: 3월 31일까지 카드가 발급되었고 그날까지 해지하지 않은 고객입니다.
2. **모델 입력**: 3월 31일까지 발생한 거래로 최근 30·90일 거래건수·금액, 마지막 구매 후 경과일, 이전 기간 대비 변화를 계산합니다. 4월 거래나 미래 해지일은 입력에 넣지 않습니다.
3. **평가 정답**: 이후 기록으로 4월 1일부터 4월 30일까지 해지했는지를 확인합니다. 전체 결과 관측 기간이 부족한 표본을 임의로 ‘미해지’로 채우지 않습니다.
4. **월별 분류기 학습**: 과거 기준일의 표본도 그 예측 기간의 결과가 모두 관측된 뒤 학습에 사용합니다.

입력과 정답 생성은 [월별 스냅샷 코드](../../src/experiments/synchrony/data.py), 학습 규칙은 [학습·평가 분리 점검](../synchrony_split_audit.md)에 정리되어 있습니다.

### 4.3 현재 단계와 남은 검증

현재는 **BankChurners 서비스 기반을 재사용하면서 시간순 해지 예측 구조로 전환하는 단계**입니다. 새 데이터의 분류 모델은 오프라인 실험으로 구현되어 있으며 기존 API·화면·캠페인에 자동 반영되지 않습니다.

남은 작업은 다음과 같습니다.

- 새 고객·거래 구조의 DB 적재와 API·화면 연결
- 캠페인 대상 자격 검증과 합성 시연 결과의 명확한 표시
- 다음 달 거래량 회귀와 행동 군집의 학습·평가
- 월별 자동 데이터 처리, 재학습, 모델 승격·롤백
- 개발에 사용하지 않은 독립 기간의 예측 성능 평가
- 해지 사유·예방 가능성 확인과 실제 개입 결과에 따른 캠페인 효과 검증

Synchrony의 실제·합성 데이터 여부와 생성 경위는 확인되지 않았으며 거래 범위는 해당 제휴몰입니다. 기록 날짜에 정보가 이용 가능했다는 가정도 필요합니다. 현재 후기 평가 기간은 이전 실험에도 사용한 자료이므로 새로운 독립 테스트 성능으로 제시하지 않습니다.

새로운 기록 구조는 미래 해지를 평가할 수 있는 기반을 제공합니다. 기존 문제 전체의 해결 여부와 실제 조기경보 성능은 서비스 전환 및 추가 검증 결과에 따라 판단합니다.
