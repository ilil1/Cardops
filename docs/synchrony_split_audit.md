# Synchrony 실험 학습·평가 분리 감사

작성일: 2026-09-25. 대상은 Synchrony 별도 실험이며 현재 CardOps의 BankChurners 서비스 모델 감사가 아니다. 추가 모델 학습 없이 코드, 원본 ZIP, 저장된 입력 표·예측·모델을 확인했다.

## 결론

**기존 결과는 각 예측 시점의 과거 자료와 미래 정답을 시간 순서대로 분리한 월별 재학습 검증이다. 영구적으로 고정해 한 번만 확인한 독립 테스트는 아니다.**

- 각 평가 시점에서 학습행과 평가행의 교집합은 0개였다. 같은 고객·같은 기준일이 양쪽에 들어간 경우도 0개였다.
- 학습에는 예측 시점까지 전체 30일 또는 60일의 결과가 관측된 과거 표본만 들어갔다.
- 같은 고객의 과거 행과 미래 행은 양쪽에 포함된다. 기존 고객의 위험을 매월 다시 평가하는 목적에 맞는 설계지만, 학습에서 한 번도 보지 못한 고객에 대한 일반화 검증과는 다르다.
- 앞선 평가월의 정답이 충분히 관측되면 뒤 평가월의 학습에 편입된다. 해당 과거 평가 예측은 다시 계산하지 않는다. 따라서 개별 시점의 미래를 미리 학습한 것은 아니지만, 전체 평가 기간이 모든 학습에서 영구 제외된 것도 아니다.
- 평가 기간을 앞선 실험에서 이미 여러 번 확인했다. 현재 결과를 완전히 새로운 독립 테스트 성능이나 미래 성능의 확정값으로 제시하면 안 된다.

## 코드에서 확인한 분리 규칙

`benchmark.train_mask`는 학습 표본 기준일을 `s`, 평가 기준일을 `t`, 예측 기간을 `h`라 할 때 다음을 모두 요구한다.

1. `s < t`
2. `s + h일 <= t`
3. 해당 표본의 정답이 결측이 아님
4. 최근 자료 모델은 추가로 `s >= t - 6개월`

평가행은 `as_of_date == t`인 표본이다. 날짜는 월말 하루가 끝난 시점으로 해석하며, 그날까지 발생한 거래·해지 상태를 사용할 수 있다는 가정이다. 실제 정보 도착 시각이나 지연은 원본에 없으므로 검증하지 못했다.

입력 생성은 `Transaction_Date <= 기준일`로 거래를 제한한다. 미래 해지일은 정답 생성과 그 기준일에 이미 해지된 고객의 제외에 사용되며, 미래 해지일까지 남은 기간을 모델 입력으로 넣지 않는다. 고객 ID, 정답 열, 최종 고객 속성 열은 모델 입력에서 제외한다.

특징 선택, 표준화, spline의 경계 학습은 모델 Pipeline 안에서 학습행으로만 수행한다. 전체 입력 표에 먼저 실행하는 `prepare_features`는 각 행의 과거 값에 대한 결정적 산술 변환이며 전체 데이터의 평균이나 정답을 학습하지 않는다.

## 실제 확인 기간의 분리

다음은 선택된 `lr_core_recent6` 모델에 적용된 분할이다. ‘라벨 확정 마지막 날짜’는 학습에 포함된 가장 늦은 기준일에 예측 기간을 더한 날짜다.

| 예측 기간 | 평가 기준일 | 학습 표본 기준일 범위 | 라벨 확정 마지막 날짜 | 학습 행 | 평가 고객 | 평가 해지 고객 | 같은 고객·같은 기준일 교집합 |
|---|---|---|---|---:|---:|---:|---:|
| 30일 | 2026-03-31 | 2025-09-30 ~ 2026-02-28 | 2026-03-30 | 171,676 | 29,790 | 305 | 0 |
| 30일 | 2026-04-30 | 2025-10-31 ~ 2026-03-31 | 2026-04-30 | 173,819 | 30,118 | 356 | 0 |
| 30일 | 2026-05-31 | 2025-11-30 ~ 2026-04-30 | 2026-05-30 | 175,872 | 30,348 | 441 | 0 |
| 30일 | 2026-06-30 | 2025-12-31 ~ 2026-05-31 | 2026-06-30 | 177,747 | 30,521 | 520 | 0 |
| 60일 | 2026-03-31 | 2025-09-30 ~ 2025-12-31 | 2026-03-01 | 113,015 | 29,790 | 631 | 0 |
| 60일 | 2026-04-30 | 2025-10-31 ~ 2026-02-28 | 2026-04-29 | 144,029 | 30,118 | 755 | 0 |
| 60일 | 2026-05-31 | 2025-11-30 ~ 2026-03-31 | 2026-05-30 | 145,754 | 30,348 | 877 | 0 |

월의 길이가 다르므로 최근 6개월 범위에 항상 6개 월말 표본이 들어가지는 않는다. 예를 들어 2026-01-31에서 60일이 지난 날은 2026-04-01이므로 2026-03-31 평가 모델의 학습에 넣을 수 없다.

비교 기준 모델은 전체 과거 학습 기간을 사용하지만 동일한 라벨 확정 규칙을 따른다. 개발 시점(2025-10-31, 2025-12-31, 2026-02-28)의 30일 모델에서도 학습·평가 키 교집합은 모두 0개였다.

## 같은 고객과 같은 행의 차이

입력 표 전체는 497,347행, 고객 34,779명, 18개 월말 기준일로 구성된다. `(customer_id, as_of_date)` 중복은 0개다.

- 30일·2026-06-30 평가 고객 30,521명 중 29,907명은 과거 학습 표본도 있다.
- 60일·2026-05-31 평가 고객 30,348명 중 29,146명은 과거 학습 표본도 있다.

예를 들어 같은 고객의 3월 말 상태를 학습하고 5월 말 상태를 평가할 수 있다. 모델에 고객 ID를 입력하지 않아도 같은 고객의 여러 관측값은 통계적으로 독립이라고 볼 수 없다. 따라서 고객을 묶어서 불확실성을 계산해야 하며, 이것을 고객 단위 완전 분리라고 부르면 안 된다.

## 앞선 평가행의 이후 학습 편입

| 예측 기간 | 뒤 평가 기준일 | 당시 학습에 편입된 이전 평가 기준일 | 편입 행 수 |
|---|---|---|---:|
| 30일 | 2026-04-30 | 2026-03-31 | 29,790 |
| 30일 | 2026-05-31 | 2026-03-31, 2026-04-30 | 59,908 |
| 30일 | 2026-06-30 | 2026-03-31, 2026-04-30, 2026-05-31 | 90,256 |
| 60일 | 2026-05-31 | 2026-03-31 | 29,790 |

이는 과거 예측의 실제 결과가 나온 뒤 다음 모델을 갱신하는 운영 시뮬레이션이다. 한 번 고정된 모델의 몇 개월 뒤 성능을 측정하는 실험과는 다른 질문에 답한다.

60일 평가의 양성 2,263행은 고유 해지 고객 1,553명이다. 한 해지 사건이 서로 겹치는 두 예측 기간에 등장할 수 있으므로 행별 적중 수의 합을 고유 해지 고객 수로 해석하면 안 된다. 30일 평가에서는 양성 1,622행과 고유 해지 고객 1,622명이 일치했다.

## 실제 산출물 교차검증

추가 학습 없이 다음을 확인했다.

- 원본 발급·해지일과 497,347개 표본의 자격을 비교: 아직 미발급이거나 이미 해지된 고객이 들어간 행 0개.
- 원본 해지일에서 다시 계산한 정답과 비교: 30일 유효 497,347행, 60일 유효 466,826행에서 불일치 0개. 관측 기간이 부족한 60일 표본에 0 또는 1이 잘못 입력된 경우 0개.
- 2025-01-31, 2026-03-31, 2026-06-30에서 각 200명씩 원본 거래로 특징 재생성: 210개 특징이 저장된 실험 입력과 수치 허용오차 1e-12 이내 일치.
- 저장된 네 예측 CSV의 고객·기준일 중복 0개. 정답이 입력 표와 전부 일치.
- 저장된 30일 최종 모델의 표준화 학습 수 177,747행, 60일 최종 모델은 145,754행으로 분할 집계와 일치. 31개 입력의 표준화 평균을 학습행에서 다시 계산했을 때 저장값과 차이 0.
- 감사 시작 시 `benchmark.py`, `models.py`의 SHA-256이 기존 30일 protocol.json의 기록과 일치했다. 이후 수정되는 코드는 별도 변경으로 취급한다.
- `test_protocol.py`의 미래 거래·정답 변경에 대한 입력 불변성, 라벨 확정 지연, 불완전 관측 처리 테스트 3개 통과.

이 검증은 확인한 데이터와 구현에서 직접적인 미래 거래·정답·전처리 누수를 발견하지 못했다는 의미다. 원본의 실제 생성 과정, 거래 누락 여부, 운영 환경의 정보 도착 시점까지 증명한 것은 아니다.

## 개발 시점과 반복 평가의 한계

실제 30일 실행은 2025-10-31, 2025-12-31, 2026-02-28의 평균 AP로 후보를 고른 뒤 2026년 3~6월을 확인했다. 마지막 개발 표본의 30일 정답은 2026-03-30까지 관측되어 첫 확인 시점 2026-03-31보다 앞선다.

실제 60일 산출물은 `benchmark --horizon 60`이 아니라 **`transfer.py` 경로**에서 생성되었다. 30일 개발 구간에서 선택한 방법을 고정하고 60일 정답으로 다시 학습·평가했다. `classification_60_transfer/protocol.json`에도 이 경로가 기록되어 있다.

감사 시작 시 범용 `benchmark.py`를 직접 `--horizon 60`으로 실행하면 개발일을 30일과 똑같이 사용하게 되어 있었다. 그러면 2026-02-28 개발 표본의 60일 정답은 2026-04-29까지 필요해 첫 확인 시점 2026-03-31보다 늦어진다. 따라서 그 경로는 방법 선택 단계에서 미래 결과를 참조할 위험이 있었다. **실제 보고된 기존 60일 결과는 이 경로를 사용하지 않았으므로 해당 잠재 문제와 구분해야 한다.** 이 감사 자체에서는 코드 수정이나 60일 재학습을 하지 않았다.

후속 수정에서는 `development_dates(horizon)`이 첫 확인 시점 전에 정답이 성숙한 개발일만 선택하도록 바뀌었다. 직접 60일 실행은 이제 2025-10-31, 2025-12-31만 개발일로 사용하며 2026-02-28은 제외한다. 30일 개발일은 유지한다. 기존 테스트 3개와 개발일 보존·라벨 성숙 검사 2개를 포함해 총 5개 테스트가 통과했다. 기존 실험 결과 파일과 과거 점수는 변경하지 않았다.

또한 기존 protocol.json은 `confirmation_reused: true`를 명시한다. 해당 확인 기간을 이미 앞선 실험에서 조회했으므로 이번 실행 내부에서 선택을 고정했더라도 사람의 특징·모델 설계가 과거 평가 결과에 영향을 받았을 가능성은 남는다. 지금 같은 자료를 다시 나누거나 새 이름으로 저장해도 과거에 보지 않은 테스트로 바뀌지는 않는다.

추가 개선은 시도할 수 있다. 다만 개선의 개발 기준을 먼저 고정하고 반복 검증 결과로 표시해야 한다. 완전히 독립적인 성능 확정에는 아직 개발에 사용하지 않은 새 시기 자료 또는 별도 모집단이 필요하다.

## 후속 고정 분할 실험 상태

별도 `strict_benchmark`는 2026-03-30에 모델을 동결하고 평가 기간 중 재학습을 하지 않는 방식으로 실행을 완료했다. 개발 기준일은 2025-08-31, 2025-10-31, 2025-12-31이며, 최종 학습에는 동결일까지 정답이 성숙한 표본만 사용한다. 따라서 최종 학습 표본 기준일의 상한은 30일 모델 2026-02-28, 60일 모델 2025-12-31이다.

후속 결과는 [고정 모델 평가 보고서](synchrony_strict_evaluation.md)에 기록했다. 전체 평가 기간과의 학습 관측 키 중복은 0이며, 평가 루프는 저장된 모델의 예측만 수행한다. 신규 후보는 직전 후보를 안정적으로 앞서지 못했다. 기존 순차 재학습 결과와 구분해야 하며, 고정 분할로 다시 실행하더라도 과거에 이미 조회한 평가 기간이라는 한계는 남는다.
